## Problem Statement

Instructor 缺少一个统一、只读的视图，将自己 Course 的 Gross sales、Enrollment Count 和 Student progress 联系起来，识别购买总额较高但学习成效较弱的课程。Admin 需要在已有全局课程权限内完成相同分析，并按 Instructor 和 Course 缩小范围。

现有课程工作区和学生名单不能直接满足跨课程聚合、日期筛选、稳定分页、部分指标重试及明确的数据缺口表达。当前数据不能支持退款调整后的 Net revenue、Retention rate 或 Instructor 教学进度；将缺失数据表示为零会误导使用者。

成功标准：授权用户可按课程范围和期间获得准确、可解释的汇总，查看获授权课程的学生快照，并清楚区分真实零、暂无数据、无法计算和查询失败。

## Solution

保留 `/instructor` 作为导师工作区入口，新增 `/instructor/analytics` 和课程级 analytics 页面。采用现有 React、Tailwind、shadcn 及原生控件，提供可分享的 URL 筛选、五张同级 KPI 卡片、逐课程摘要和课程级学习成效及学生表。

首版通过现有数据库实时读取；analytics service 统一处理授权和聚合，loader 处理 session、参数校验及编排。功能只读，不添加运营操作。没有数据基础的指标保留 `/` 和直接可读的解释。

## User Stories

1. As an Instructor, I want to keep the existing instructor workspace, so that I can continue managing courses while accessing analytics separately.
2. As an Instructor, I want an overview of all courses I own, so that I can compare purchase totals and student learning outcomes.
3. As an Instructor, I want to select one owned course, so that I can narrow the analytics scope.
4. As an Instructor, I want other instructors' courses excluded from every result, so that student information and business data remain authorized.
5. As an Admin, I want an all-course overview, so that I can understand platform-wide course performance within my existing permissions.
6. As an Admin, I want to filter by instructor and then course, so that I can investigate a smaller authorized scope.
7. As an Admin, I want invalid dependent course selections cleared when I change instructor, so that the results match the visible filters.
8. As an authorized viewer, I want all history selected by default, so that the initial view has a predictable scope.
9. As an authorized viewer, I want last-seven-days, last-thirty-days, last-year and all-history shortcuts on desktop and mobile, so that common periods are easy to select.
10. As an authorized viewer, I want custom dates interpreted in the application timezone with an inclusive start and exclusive end, so that boundary records are counted predictably.
11. As an authorized viewer, I want field-level errors for invalid dates, ranges, enums and page numbers, so that I can correct the relevant filter.
12. As an authorized viewer, I want valid future periods to show normal empty results, so that an empty period is not treated as invalid input.
13. As an authorized viewer, I want filters and list pages represented in the URL, so that I can reload or share a view.
14. As an authorized viewer, I want relevant pagination reset after filter changes, so that an old page does not obscure the new result.
15. As an authorized viewer, I want Purchase Total to sum recorded purchases before refunds, so that I understand what the amount actually measures.
16. As an authorized viewer, I want zero purchase totals displayed as currency, so that an aggregate is not mistaken for a free course price.
17. As an authorized viewer, I want Enrollment Count to count distinct student-course relationships, so that duplicate enrollment rows do not inflate it.
18. As an authorized viewer, I want Average Student Learning Progress to represent lesson completion, so that it is not confused with instructor teaching progress.
19. As an authorized viewer, I want learning progress labeled as a current snapshot of eligible enrollments, so that I do not mistake it for a historical trend.
20. As an authorized viewer, I want Retention Rate and Net Revenue to remain visible with explanations of missing data, so that I understand the reporting limitations.
21. As an authorized viewer, I want a paginated course summary with explicit course links, so that I can compare courses and open details while keeping my dates.
22. As an authorized viewer, I want the overview to remain available even if I have only one course, so that navigation is consistent.
23. As an authorized course viewer, I want a course learning-outcomes panel, so that progress, quiz score, participating students and quiz count have clear course context.
24. As an authorized course viewer, I want each student's best in-period attempt per quiz used in quiz reporting, so that repeated attempts do not distort the result.
25. As an authorized course viewer, I want quizzes without participants excluded from score averages, so that missing attempts are not treated as failures.
26. As an authorized course viewer, I want unavailable progress or quiz metrics explained when there are no lessons or quizzes, so that absence is not shown as zero performance.
27. As an authorized course viewer, I want full student names and emails alongside enrollment date, progress and quiz average, so that I can interpret the authorized roster.
28. As an authorized viewer, I want the all-courses overview to contain no student PII, so that aggregate analysis does not expose a cross-course roster.
29. As an authorized course viewer, I want only currently existing, in-period enrollments in student snapshots, so that deleted membership is not invented.
30. As an authorized viewer, I want both lists to use stable sorting and twenty rows per page, so that I can navigate results predictably.
31. As an authorized viewer, I want distinct messages for no authorized courses, no period data and no eligible course students, so that I understand how to proceed.
32. As an authorized viewer, I want successful metrics preserved if another metric fails, so that one failure does not hide usable results.
33. As an authorized viewer, I want Retry to reload only the failed metric and show its new query time, so that I can recover without confusing the age of other values.
34. As an authorized viewer, I want initial skeletons and explicit Updating states during refetch, so that loading does not resemble missing data.
35. As a keyboard or screen-reader user, I want accessible filters, links, pagination, retry and loading announcements, so that I can operate the dashboard independently.
36. As a mobile viewer, I want a scrollable student table with a sticky Name column, overflow hint and scroll shadows, so that identity remains visible while reading all columns.
37. As an authorized viewer following a bookmarked course URL, I want current authorization checked on every load, so that deleted courses and ownership changes are handled correctly.

## Implementation Decisions

- **Scope and routing:** retain the existing workspace and add overview and course-scoped analytics routes. A course-scoped route uses the current course identity and reauthorizes on every load. Register routes through the project's actual explicit React Router configuration. The overview remains available with one course; do not automatically redirect it.
- **Service boundary:** introduce a tested analytics service over the existing shared Drizzle/SQLite connection. It owns authorized course selection, aggregate calculations, course summaries, student snapshots and individual metric retry. Loaders obtain session identity, validate parameters and orchestrate calls. Use grouped/batched queries rather than querying separately for each course, student or quiz. No new database connection, preaggregation table or snapshot table is required.
- **Authorization:** Instructor scope is owned courses; Admin scope follows the existing global Admin boundary. Every aggregate and detail query applies the service's authorized course IDs. No authorized courses is a successful empty workspace; an explicitly requested existing course outside the viewer's permissions is an authorization error. Deleted courses return not found. Unavailable courses are omitted from selectors. Scope authorization failures block the response and are not converted into one failed metric.
- **PII:** full Name and Email appear only inside an authorized single-course student table, identically for Instructor and Admin. All-courses summaries carry no student PII. Do not introduce cross-course student search or a cross-course roster.
- **Filters:** Instructor defaults to all owned courses; Admin defaults to all courses, with optional Instructor then Course narrowing. Date presets are last seven days, last thirty days, last year and all history; presets remain visible on mobile. Custom ISO calendar dates use application timezone boundaries, start inclusive and end exclusive. Default is all history.
- **URL behavior:** encode date, role-relevant filters, course-summary page and student-table page. Omitted values mean all history, all authorized courses and page one. Malformed dates, illegal page numbers/enums and start greater than or equal to end produce field-level errors. Valid future periods execute normally. Date, Instructor or Course changes reset relevant pagination. Changing Admin Instructor clears a now-invalid dependent Course, refreshes options and queries the valid Instructor scope; this is not permission to silently normalize an explicit unauthorized course request. Course navigation preserves dates.
- **Purchase Total:** sum integer-cent `purchases.pricePaid` over authorized courses using `purchases.createdAt` in the period. Count each purchase primary key once, including separate rows with identical business contents; do not content-deduplicate or subtract refunds. Avoid join multiplication. Return cents and the application's configured single currency; never infer currency from country. Reuse `formatPrice()` where compatible, with aggregate zero formatted as the currency's zero amount rather than `Free`.
- **Enrollment Count:** filter `enrollments.enrolledAt` by the period and count distinct student-course relationships. Across courses, the same student in two courses contributes two relationships. Cross-course student deduplication applies only to a field explicitly named as a student count.
- **Student snapshot and progress:** use enrollment rows still present at query time with an in-period enrollment date. Exclude enrollments begun before the period and do not reconstruct removed rows. Compute completed lesson count divided by total course lesson count for the eligible student-course population. Pool completed and possible student-lesson units across courses rather than averaging rounded percentages or giving each course equal weight. Aggregate at full precision and round displayed progress to a whole percentage. No calculable lessons means unavailable, not zero. Display snapshot time; this is Student progress, never Instructor teaching progress.
- **Quiz outcomes:** filter attempts by `quiz_attempts.attemptedAt`, applying authorized course scope. Retain each student's best score for each quiz within that period, then calculate course quiz reporting by averaging quizzes using those best scores. Exclude quizzes with no participating students from the average denominator. Participating Students counts distinct students with at least one included attempt. Do not substitute zero for no attempt. Keep calculation precision until displaying a one-decimal score; existing scores use a fractional scale and existing UI presents percentages. A student row's quiz average uses that student's included best attempts. No quizzes means unavailable; existing quizzes with no in-range attempts yield an empty score. Enrollment-date eligibility governs the student snapshot and must not silently replace attempt-date filtering for course quiz metrics.
- **Metric states:** each metric is explicitly `value`, `empty`, `unavailable` or `error`; only `value` carries numeric data, all other states carry stable reason codes mapped to presentation text. A real zero requires supporting data, such as a recorded zero-value purchase or an eligible student with no completed lessons. No matching records renders empty. Preserve the project's outer service result convention of `ok` success/failure; metric states are payloads within an authorized successful response, not replacements for whole-request authorization errors.
- **Unavailable metrics:** Retention Rate and Net Revenue remain in the overview grid as `/`, with inline explanations of missing activity/refund records. Do not use a weakened background or tooltip-only explanation. No-lessons/no-quizzes explanations are specific to the relevant course metric.
- **Consistency and retry:** return a shared server-generated `asOf` for initial results, including progress and student snapshots. Use one read-consistency boundary supported by existing SQLite transactions; otherwise explicitly label values as approximate live reads under the shared timestamp. Independent retry recalculates only the failed metric and updates its `asOf` and the response refresh indication; make clear that other cards retain their earlier observation times. Do not imply retry refreshed the entire snapshot. Refresh on initial load, filter changes and explicit retry; no automatic polling.
- **Partial failure:** retain successful cards. A failed metric displays `Unable to load this metric`, a safe reason-specific explanation and `Retry`. Do not expose internal database details. Initial loading uses geometry-matching skeletons. Refetch preserves previous successful values with page-level `Updating` near scope/as-of and inline status on affected metrics; prevent conflicting submissions and do not present stale values as already matching newly selected filters.
- **Overview layout:** desktop order is title/scope, horizontal filters, KPI grid, course summaries, and a student table only when the scope authorizes a single-course roster. Mobile uses compact stacked sections and expandable native filter fields, with date presets always visible. Same-sized overview cards are Purchase Total, Enrollment Count, Average Student Learning Progress, Retention Rate and Net Revenue. No overview quiz card.
- **Course summaries:** show Course name, Purchase Total, Enrollment Count and Average Student Learning Progress. Latest confirmed presentation decisions reserve quiz details for the course-scoped page. Mobile summaries stack without horizontal scrolling. Only the course name or explicit `View Analytics` link navigates; the entire row is not clickable. Preserve visible hover and keyboard focus styles.
- **Course learning-outcomes panel:** use Course Average Student Learning Progress as the primary metric, with Average Best-Attempt Quiz Score, Participating Students and quiz count in the same course context. An optional CSS progress bar must not imply zero when data is unavailable.
- **Student table:** column order is Name, Email, Enrollment Date, Average Progress and Best-Attempt Quiz Average. No action or last-activity column. Use comfortable row spacing. Mobile retains these columns in a horizontally scrollable table with sticky Name and a visible boundary. When overflow is detected and the table enters the viewport, show a text hint and scroll shadows. The text may disappear after user scrolling; shadows remain an overflow affordance. Keyboard scrolling must work.
- **Pagination:** both lists use fixed twenty-row server-side pages. Course order is title ascending, then primary key ascending. Student order is enrollment date descending, display name ascending, then student primary key ascending. Summary pagination never changes KPI scope. Controls read Previous, Page X of Y and Next; current page is noninteractive, navigation labels include destination page numbers, and disabled states use more than opacity.
- **Accessibility and empty states:** distinguish 暂无可查看的课程, 所选期间暂无数据 and 该课程暂无符合条件的学生, with a relevant filter/navigation action when available. State meaning never relies solely on color. Decorative skeletons are `aria-hidden`; one live region announces Loading analytics or Updating analytics. Filters, links, pagination, retry and refresh/error notifications support keyboard and screen-reader use with visible focus.
- **Project conventions:** reuse existing components and `cn()` for composed Tailwind classes; no additional UI library. Follow object parameters for repeated same-type arguments, internal import aliases and inferred/explicit safe TypeScript types without `any`. Keep money in integer cents and timestamps in ISO text. No schema change or deletion workflow change is included; preserve existing security measures.

## Testing Decisions

The user confirmed the following testing seams on 2026-09-23. Test externally visible results and behavior; do not lock SQL strings, internal helper structure, component class lists or query call order.

1. **Primary seam — analytics service public operations with real test SQLite.** Follow `purchaseService.test.ts`, `enrollmentService.test.ts`, `progressService.test.ts` and authorization-oriented `courseCommentService.test.ts`. Use existing `createTestDb()` migrations and `seedBaseData()` in `beforeEach`, and the prescribed getter mock for the shared database before importing the service. Add accompanying tests for the new service. Most authorization, scope, aggregation, snapshot, pagination and state cases belong here; no separate calculation-only abstraction is needed merely for testing.
2. **Thin HTTP/loader seam — session and URL behavior.** Follow the course-detail and lesson-route Vitest tests, directly invoking loaders with Request objects, a mocked session identity and the test database. Verify session handling, role rejection, field errors, normalized defaults, course authorization/not-found mapping, filter cascade, date preservation and retry scope. Do not duplicate every arithmetic fixture at this boundary. Ensure payloads never contain cross-scope student PII.
3. **Rendered UI and browser acceptance — presentation and interaction.** Existing `rating-summary.test.tsx` uses static React rendering for visible values and text; reuse that style for four-state presentation and accessible attributes. Static rendering cannot prove focus, keyboard interaction, live-region announcements, viewport overflow or request transitions. Exercise those through focused real-browser/manual acceptance using the eventual low-fidelity prototype and implemented routes; no installed browser-test framework is assumed or required by this spec.

Acceptance cases:

- Instructor owns course A but not B; every overview, course detail and retry respects that boundary. Admin sees both and can narrow by owner. A Student cannot access analytics. Empty authorized scopes succeed; deleted courses return not found and existing unauthorized courses return authorization error, including after an ownership change.
- URL omissions normalize to all-history/all-authorized/page-one. Malformed and impossible dates, illegal pages/enums and reversed/equal boundaries return field errors. Records exactly at start are included; exactly at end excluded after application-timezone conversion. Valid future ranges render empty. Instructor changes clear invalid dependent courses and reset pages while preserving the remaining valid scope.
- Two distinct purchases with identical contents both count once. Multiple enrollment/quiz joins do not multiply their cents. A recorded zero purchase displays a currency zero; an absence of purchases displays empty. Duplicate enrollments do not inflate distinct relationship counts or student progress weighting. One student in two courses contributes two enrollment relationships.
- Best-attempt selection ignores out-of-period attempts even when higher, and counts each student-quiz pair once. Quizzes without participants contribute no denominator entry. Use fixtures with unequal quiz participation to expose unintended weighting; preserve the confirmed averaging-quizzes definition. Participating Students deduplicates across quizzes. Absence of attempts never becomes zero score.
- No lessons/no quizzes produce unavailable explanations. Eligible students with lessons but no completions have real zero progress. Pooled progress is tested with different course sizes and rounds only after aggregation. Removed enrollments and enrollments before the selected period are excluded from snapshots even if progress records remain.
- Explicitly verify all four states and stable reasons. Inject a recoverable metric read failure at an existing database/service dependency boundary; successful siblings remain available, safe error text is rendered, and Retry updates only the failed result and its observation time. Whole-scope authorization failure never leaks partial data.
- Initial response timestamps are shared; a retry clearly identifies mixed observation times. Pagination fixtures exceed twenty rows and include equal titles/names/dates to verify tie-breaking, fixed page size, no cross-page overlap on unchanged data, and page-independent aggregate totals.
- PII appears only in authorized course detail; overview result and markup omit student name/email. Verify one-course overview stability and date-preserving explicit links.
- Desktop/mobile acceptance covers same-sized five-card grid, no overview quiz card, course-only quiz details, permanent mobile date presets, twenty-row pagination and specified table column order. Check genuine zero, all three empty messages, slash explanations and safe retry errors.
- Keyboard/screen-reader acceptance covers focus visibility, filter changes, disabled conflicting submissions, pagination destination labels, noninteractive current-page status, one loading live region, hidden decorative skeletons and announced refreshed/error results. Verify stale values are visibly Updating, retry affects one metric, sticky Name has a boundary, overflow hint appears on viewport entry and keyboard scrolling works after the hint dismisses.

This spec does not claim implementation tests have run. This phase creates requirements only.

## Out of Scope

- Course editing, contacting students, issuing refunds, changing enrollment, sending messages, export and cross-course student search.
- Refund-adjusted net revenue, retention calculation, lesson drop-off, historical progress trends, instructor teaching-progress measurement and real-time event streaming.
- Automatic polling, adjustable page size or table density, cross-course PII rosters, new external UI libraries, preaggregation/snapshot tables, or broad cleanup of legacy services.
- New hashes, frozen contracts, baselines or gates. Normal types, primary keys, transactions and behavior tests are sufficient for this feature's stated needs.
- Implementation, prototype production and ticket creation during this spec phase. A later low-fidelity prototype covers layout, role filters, four metric states, twenty-row pagination, scoped PII and course navigation before UI implementation; service/route work does not require a prototype. Ticket decomposition occurs only after spec approval and a separate request.

- The source defines quiz reporting as best attempts followed by averaging quizzes, but contains an earlier general pooling statement. Duplicate enrollment rows are not prohibited by the current schema; the confirmed relationship count is clear, while choice of displayed enrollment date for conflicting duplicate timestamps is not specified by the source.
