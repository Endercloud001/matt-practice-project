# Clean Up

在功能开发或验收阶段结束、需要整理项目目录时使用。目标是先产出一份可复核的 `clean-list.md`，让用户能看清哪些内容必须保留、哪些内容可以清理，以及每个判断依赖的证据。除非用户另行明确要求执行清理，否则不要删除、移动、暂存、提交或推送文件。

## 盘点流程

1. 先确定范围和基线。读取项目根目录的 `AGENTS.md`、`CONTEXT.md` 以及与任务相关的 `docs/agents/`、ADR 和规格；确认项目根目录、当前分支、当前 worktree、上游分支和相关 issue/PR。使用只读命令检查 `git status --short --ignored`、`git worktree list`、`git branch -vv`、跟踪文件和当前差异，并核对是否存在未提交内容或未合并状态。不要把未跟踪或被 `.gitignore` 忽略直接当作无用。
2. 探索候选内容。检查构建目录和缓存（例如 `build/`、`dist/`、`.react-router/`、`.cache/`）、运行日志、PID 文件、临时截图、浏览器/验收脚本、故障注入脚本、夹具和响应快照、旧计划/交接/PR 草稿、旧实现，以及项目外但由当前仓库登记的 worktree、分支和 stash。用配置、脚本、文档链接、Git 内容和进程状态判断是否仍被使用；不要只凭文件名、修改时间或 `.gitignore` 分类。
3. 为每个候选记录证据：相对或绝对路径、是否被 Git 跟踪、是否仍被源码/测试/配置/文档引用、能否重新生成、是否包含唯一决定或验收证据、是否有正在运行的进程依赖，以及清理前需要满足的条件。路径通配符必须限定在已写明的目录内。
4. 先写“明确保留”。至少检查并按实际项目情况保留当前未提交修改、`.agents/`、`AGENTS.md`、`CONTEXT.md`、`.gitignore`、业务源码/测试/迁移、依赖清单和锁文件、运行配置、数据库及其 WAL/SHM 配套文件、凭据和用户数据、现有 `node_modules/`（除非用户明确要求且确认可重建）、仍被引用的文档、最终验收结论、尚未被替代的故障注入脚本和过程截图、唯一的人工验收证据，以及本次生成的清单。保留项优先于目录级删除；整目录退役前必须先迁出独有内容。
5. 处理 issue、组件、脚本和工作区的分歧。以当前本地工作树和可确认的最新远端跟踪引用为基线，比较提交祖先关系和文件内容；有未提交本地修改时，把它视为当前本地状态的一部分。不要只用文件系统时间推断新旧，也不要假定远端跟踪引用已经刷新；确需确认远端且网络可用时可做只读查询，不能把不完整的远端信息当作事实。远端状态无法确认时在清单中说明。旧 issue 副本只有在其独有内容已被基线覆盖或明确不再需要时才列入清理；无法证明时列为“需要用户审查”。原型工作区和分支是需求决策来源时，应先提取其独有决定再处理。
6. 生成清单。默认写到 `docs/<范围>-clean-list.md`；没有明确范围时写到 `docs/clean-list.md`，若调用者指定了路径则遵循指定路径。使用 [references/clean-list-template.md](references/clean-list-template.md) 的结构：保留项必须位于其他候选项之前，并按可重建产物、临时日志/截图/验收资料、旧文档与交接、旧实现与一次性脚本、worktree/分支/stash 分组。每一项都写清建议、理由、前置条件和证据；不确定项单独列出，不伪装成可安全删除。
7. 在清单末尾记录建议的执行顺序和检查项，但把它们标为“用户明确选择执行后才进行”。执行顺序应包括重新检查 Git 状态、停止并确认相关进程、迁出保留材料、验证绝对路径边界、逐项清理、检查链接和正式源码/测试/配置。使用 `git worktree remove` 管理 worktree，不直接删除其 `.git` 文件或共享仓库元数据；stash 只能在核对精确提交和说明后处理。不要因为本 skill 自动修改 `.gitignore`、创建 hash/冻结 contract/baseline/gate、暂存或提交变更，也不要删除本地或远端分支，除非用户另行明确要求。

## 输出质量

- 清单开头说明盘点日期、项目根目录、当前分支/提交、远端引用和“只记录建议，尚未执行”的状态。
- 保留项要先于删除候选项，且不能用“整目录删除”掩盖目录中的数据库、配置、规范或验收材料。
- 每个候选路径都必须能由读者在当前机器上定位；路径缩写要给出绝对路径展开，通配符要给出作用范围。
- 对运行中的服务、浏览器、采集脚本和数据库，只记录停止或备份前提，不凭 PID 数字直接终止进程。
- 清单本身属于清理记录，应列入保留项。若清单被 `.gitignore` 忽略，记录这一事实，不要为此擅自修改忽略规则。
